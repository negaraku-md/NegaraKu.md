บทความจัดอันดับซอฟต์แวร์บัญชีของมาเลเซียเป็นแนวที่ตายตัว คือมีสิบผลิตภัณฑ์ อธิบาย
อย่างละหนึ่งย่อหน้า ตารางคุณสมบัติที่ไม่มีใครใช้ และลิงก์แบบพันธมิตร มันไม่เคยมีประโยชน์
และนับตั้งแต่ e-Invoice และ MBRS 2.0 มาถึง มันก็กลายเป็นสิ่งที่ทำให้เข้าใจผิดอย่างจริงจัง
เพราะมันจัดอันดับผลิตภัณฑ์บนสิ่งที่ไม่ได้แยกความแตกต่างของผลิตภัณฑ์เหล่านั้นอีกต่อไป

สองความสามารถต่างหากที่แยกความแตกต่างของผลิตภัณฑ์ในปัจจุบัน และทั้งสองอย่างไม่ปรากฏ
บนตารางคุณสมบัติ

## แกนที่ 1: ซอฟต์แวร์นำเอกสารเข้าสู่ MyInvois อย่างไร

LHDN บันทึก **กลไกการส่งข้อมูลสองแบบ** คือ MyInvois Portal และ API และแยกต่างหาก
โดยอนุญาตให้ผู้เสียภาษีแต่งตั้ง **ตัวกลาง** เพื่อยื่นแทนตนได้ สิ่งนี้ก่อให้เกิดรูปแบบใน
ทางปฏิบัติสี่แบบ และซอฟต์แวร์ที่ท่านซื้อจะกำหนดว่าแบบใดเปิดให้ท่าน

| เส้นทาง | สิ่งที่ซอฟต์แวร์ต้องทำ | สิ่งที่ต้องตรวจสอบ |
| --- | --- | --- |
| **พอร์ทัลอย่างเดียว** | ไม่ต้องทำอะไร ท่านคีย์หรืออัปโหลดเป็นชุดใน MyInvois | ซอฟต์แวร์สามารถส่งออกไฟล์ที่ตรงกับรูปแบบสเปรดชีตอัปโหลดชุดของพอร์ทัลได้หรือไม่ หรือเป็นการคีย์ใหม่ |
| **API โดยตรง** | สร้างและลงนามเอกสาร UBL 2.1 จัดการโทเคน จัดการการตรวจสอบความถูกต้องแบบไม่ประสานเวลา | การแปลเป็นภาษาท้องถิ่นของมาเลเซียครอบคลุมประเภทเอกสารแบบออกใบแจ้งหนี้ให้ตนเอง (self-billed) และช่องข้อมูลภาคผนวกการนำเข้าหรือไม่ ไม่ใช่เพียงใบแจ้งหนี้ขายมาตรฐาน |
| **ผ่านตัวกลางหรือมิดเดิลแวร์** | ส่งออกข้อมูลรายการที่สะอาดตามกำหนดเวลา | การยื่นใช้ข้อมูลรับรองของใคร ใครถือข้อมูล และอะไรออกไปกับท่านเมื่อท่านออก |
| **ผ่านผู้ให้บริการ Peppol** | เหมือนกับมิดเดิลแวร์ ผ่านจุดเข้าถึง Peppol | ว่าท่านจำเป็นต้องมีการแลกเปลี่ยนที่ทำงานร่วมกันได้กับคู่ค้าจริงหรือไม่ Peppol ไม่ใช่ข้อกำหนดของ MyInvois |

การเลือกระหว่างเส้นทางเหล่านี้เป็นคำถามเรื่องปริมาณและสถาปัตยกรรมที่กล่าวถึงใน
[การเชื่อมต่อ MyInvois](/th/taxation/myinvois-integration) สิ่งที่เกี่ยวข้องในที่นี้คือ
ผลที่เกิดขึ้นในฝั่งซอฟต์แวร์ คือโปรแกรมที่ไม่มีเส้นทางการเชื่อมต่อ API ไม่ได้หยุดท่านจาก
การปฏิบัติตามกฎหมาย แต่ผูกมัดให้ท่านใช้พอร์ทัล และต้นทุนของพอร์ทัลคือการกดแป้นพิมพ์
และการกระจุกตัวในช่วงสิ้นเดือน มากกว่าค่าธรรมเนียมใบอนุญาต

**รายละเอียดเรื่องตัวกลางที่ควรเขียนลงในสัญญา:** ตัวกลางสามารถดูและเรียกดูได้เฉพาะ
ใบแจ้งหนี้อิเล็กทรอนิกส์ที่ตนยื่นเองเท่านั้น เปลี่ยนผู้ให้บริการแล้วประวัติการยื่นของท่าน
จะไม่ตามท่านไป จงวางแผนการทำงานคู่ขนานและเก็บคลังของท่านเอง

## การกล่าวอ้างการรับรองที่ควรไม่ไว้วางใจ

LHDN เผยแพร่ SDK เอกสาร API และคำถามที่พบบ่อย แต่ไม่ได้เผยแพร่ระบบการรับรอง
โครงการออกใบรับรอง หรือรายชื่อผู้ขายที่ได้รับอนุมัติสำหรับซอฟต์แวร์ e-Invoice หาก
ผลิตภัณฑ์ถูกทำการตลาดว่า **ได้รับอนุมัติจาก LHDN** สถานะนั้นเป็นคำอธิบายของผู้ขาย
เกี่ยวกับตัวเอง จงขอดูตราสารนั้น

มีการรับรองที่แท้จริงหนึ่งเดียวในระบบใบแจ้งหนี้อิเล็กทรอนิกส์ของมาเลเซีย และมันเป็นของ
ผู้อื่น **MDEC เป็น Peppol Authority ของมาเลเซีย** และรับรองสองบทบาทที่แตกต่างกัน

| บทบาท | คืออะไร |
| --- | --- |
| **Peppol Service Provider (SP)** | ดำเนินการจุดเข้าถึง Peppol ซึ่งเป็นเกตเวย์การเชื่อมต่อที่กำหนดเส้นทางเอกสาร |
| **Peppol-Ready Solution Provider (PRSP)** | สร้างซอฟต์แวร์หรือ ERP ที่สอดคล้องกับ Peppol สำหรับผู้ใช้ปลายทาง |

รายชื่อทั้งสองเผยแพร่โดย MDEC ทั้งสองไม่ใช่การอนุมัติของ LHDN และทั้งสองไม่จำเป็นต่อ
การปฏิบัติตามข้อบังคับ e-Invoice ผู้ขายที่มีการรับรองจาก MDEC ได้แสดงความสอดคล้อง
ตามมาตรฐาน Peppol ซึ่งเป็นข้อรับรองที่แท้จริง สำหรับ Peppol

## แกนที่ 2: ผลลัพธ์สามารถป้อนเข้าสู่การยื่น MBRS ได้หรือไม่

นี่คือข้อเท็จจริงที่จัดกรอบใหม่ให้ทั้งหมวดหมู่ คือ **ไม่มีโปรแกรมบัญชีใดยื่นงบการเงินต่อ
SSM ได้**

การยื่นถูกจัดทำใน **เครื่องมือเตรียม MBRS (MBRS Preparation Tool หรือ mTool)** ของ
SSM เอง ซึ่งสร้างไฟล์ zip ที่อัปโหลดไปยังพอร์ทัล MBRS นั่นคือสิ่งประดิษฐ์การยื่นที่ได้รับ
การยอมรับ ไม่ว่าบัญชีแยกประเภทของท่านจะผลิตอะไรออกมา มันจะกลายเป็นการยื่น MBRS
ก็ต่อเมื่อผ่านเครื่องมือดังกล่าวแล้วเท่านั้น

ดังนั้นคำว่าพร้อมสำหรับ MBRS ในฐานะการกล่าวอ้างของซอฟต์แวร์ จึงมีความหมายได้อย่าง
ซื่อสัตย์เพียงอย่างเดียว คือผลลัพธ์อยู่ในรูปแบบที่แมปกับอนุกรมวิธาน **SSMxT** ของ SSM
ได้อย่างสะอาด สามคุณสมบัติเป็นตัวตัดสินเรื่องนี้

- **งบทดลองที่เสถียรและส่งออกได้** พร้อมรหัสบัญชีที่ไม่เปลี่ยนแปลงในแต่ละปี การแมปจะถูกสร้างใหม่ทั้งหมดเมื่อรหัสเปลี่ยน
- **เกณฑ์การแสดงรายการที่ไม่เลื่อนไหล** การสลับระหว่างรูปแบบการแสดงรายการบังคับให้ต้องทำการแมปใหม่แม้ตัวเลขจะเหมือนกันก็ตาม
- **ผังบัญชีที่แต่ละบรรทัดมีที่ลง** สถาปัตยกรรม SSMxT ระบุว่านิติบุคคล **ต้องไม่ขยายอนุกรมวิธาน** การขยายเฉพาะบริษัทเป็นสิ่งต้องห้าม และรายละเอียดต้องอยู่ในบล็อกข้อความ บัญชีที่ไม่มีแนวคิดที่ตรงกันคือการตัดสินใจด้วยมือทุกปี

มีกับดักเชิงกลไกสองอย่างอยู่ในกระบวนการถัดไปและควรทราบก่อนจะโทษซอฟต์แวร์ ค่าใช้จ่าย
ถูกเก็บเป็นค่า **บวก** ใน SSMxT ซึ่งตรงกันข้ามกับการส่งออกจากบัญชีแยกประเภทส่วนใหญ่
และตัวเลขที่แสดงเป็นหลักพันต้องมีแอตทริบิวต์ `decimals` ที่ถูกต้อง หากผิดจะผ่านการ
ตรวจสอบความถูกต้องอย่างเงียบ ๆ และยื่นตัวเลขที่ใหญ่หรือเล็กกว่าความเป็นจริงหนึ่งพันเท่า

## รายการตรวจสอบเพื่อประเมินที่ส่งให้ผู้ขาย

1. ปัจจุบันผลิตภัณฑ์รองรับกลไกการส่งข้อมูล MyInvois แบบใด การส่งออกจากพอร์ทัล API โดยตรง หรือการยื่นผ่านบริการตัวกลางของท่านเอง
2. หากเป็น API การแปลเป็นภาษาท้องถิ่นครอบคลุมใบแจ้งหนี้อิเล็กทรอนิกส์แบบ **ออกให้ตนเอง** (self-billed) และช่องข้อมูลภาคผนวกสำหรับสินค้านำเข้าหรือไม่ หรือเฉพาะใบแจ้งหนี้ขายมาตรฐาน
3. เอกสารถูกยื่นด้วยข้อมูลรับรองของใคร และใครถือเอกสารที่ผ่านการตรวจสอบความถูกต้องแล้ว
4. เราสามารถส่งออกงบทดลองที่สมบูรณ์พร้อมรหัสบัญชีที่เสถียร ในรูปแบบที่เครื่องอ่านได้ โดยไม่ต้องมีที่ปรึกษาได้หรือไม่
5. ท่านมีการรับรองจาก MDEC ในฐานะ Peppol SP หรือ PRSP หรือไม่ และหากท่านอ้างว่าได้รับอนุมัติจาก LHDN เอกสารใดเป็นหลักฐาน
6. เมื่อออก อะไรออกไปกับเรา บัญชีแยกประเภท การแมป หรือประวัติการยื่น

## เหตุใดหน้านี้จึงไม่ระบุชื่อผลิตภัณฑ์

เพราะความสามารถจะเผยแพร่ได้ก็ต่อเมื่อผู้ขายหรือ LHDN เผยแพร่มัน และหน้าความสามารถ
ของผู้ขายเปลี่ยนแปลงระหว่างการออกเวอร์ชันโดยไม่มีบันทึกการเปลี่ยนแปลง การเปรียบเทียบ
ผลิตภัณฑ์ที่เขียนในวันนี้คือภาพนิ่งของข้อความทางการตลาด ไม่ใช่ของซอฟต์แวร์ รายการ
ตรวจสอบข้างต้นอยู่ได้นานกว่าภาพนิ่งนั้น ในขณะที่ตารางจัดอันดับอยู่ไม่ได้

## ข้อผิดพลาดที่พบบ่อย

- **การเชื่อการกล่าวอ้างว่าได้รับอนุมัติจาก LHDN** LHDN ไม่ได้เผยแพร่รายชื่อดังกล่าว
- **การสับสนระหว่างการรับรอง Peppol ของ MDEC กับการอนุมัติของ LHDN** หรือการถือว่า Peppol เป็นข้อบังคับ
- **การซื้อปุ่มยื่น** ไม่มีสิ่งใดยื่นต่อ MBRS ได้นอกจากผลลัพธ์ของ mTool
- **การอ่านคำว่าพร้อมสำหรับ MBRS ว่าเป็นการรับรอง** อย่างดีที่สุดมันหมายถึงการส่งออกที่สะอาดและเสถียร
- **การเปลี่ยนผังบัญชีทุกปี** และจ่ายค่าการแมปซ้ำในแต่ละครั้ง
- **การประเมินเฉพาะการออกใบแจ้งหนี้ขาย** ปริมาณการออกใบแจ้งหนี้ให้ตนเองคือสิ่งที่ทำให้การนำไปใช้ส่วนใหญ่พัง
- **การสันนิษฐานว่าการตรวจสอบความถูกต้องจะจับข้อผิดพลาดเรื่องมาตราส่วน** ข้อผิดพลาดมาตราส่วนหนึ่งพันเท่าผ่านไปได้

## อ่านต่อ

จงทำการทดสอบสองอย่างกับสิ่งที่ท่านมีอยู่แล้วก่อนจะเลือกซื้อ ส่งออกงบทดลองที่สมบูรณ์
และตรวจสอบว่าทุกบัญชีมีที่รองรับใน SSMxT ที่ชัดเจนหรือไม่ จากนั้นนำรายการแบบออก
ใบแจ้งหนี้ให้ตนเองหนึ่งรายการ เช่น ค่าคอมมิชชันตัวแทนหรือผู้ขายต่างประเทศ แล้วติดตาม
มันตั้งแต่ต้นจนจบเข้าสู่ MyInvois สิ่งใดในสองอย่างนี้ที่ล้มเหลวคือสิ่งที่ท่านกำลังซื้ออยู่จริง
