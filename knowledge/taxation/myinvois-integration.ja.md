この判断について書かれたもののほとんどは、いずれかの答えを売っている誰かによって書かれている。だから、LHDNが実際に認めている二つのメカニズムだけから出発しよう——e-Invoice GuidelineのTable 2.1に載っている、**MyInvoisポータル**と**API**である。Peppolプロバイダー、非Peppol技術プロバイダー及びミドルウェアは第三の選択肢ではない——それらはAPIへ到達するための三つの経路である。

## 二つのメカニズム

| | MyInvoisポータル | API |
| --- | --- | --- |
| コスト | **MyTax**ログイン経由で無料 | 構築又はライセンス取得 |
| 入力方法 | 逐一のフォーム入力、または**あらかじめ定められたExcelスプレッドシートの一括アップロード** | **UBL 2.1**に従ったXMLまたはJSON |
| 署名 | ポータルが処理 | 自社の**デジタル証明書**（.cerまたは.pfx） |
| LHDNが示す適合先 | すべての納税者が利用可能；API接続が使えない事業者 | 大量向け；事前の投資とシステム変更を要する |
| 経路 | 一つ | 直接ERP、**Peppol**プロバイダー、**非Peppol**プロバイダー |

どちらも同じものを生み出す——IRBM固有識別番号、検証タイムスタンプ、そして視覚的表示に付されるQRコードである。

## 買う前に問題の規模を測る

問われているのはあなたの売上ではない。**毎月何件の文書を伝送しなければならないか**であり、その件数は通常、人が予想するより多い。

1. 電子インボイスを求めた買い手向けの個別取引電子インボイス
2. 統合電子インボイス——月に1件以上、支店ごとに分ける場合は支店ごとに
3. **自己請求電子インボイス**——手数料、海外の供給者、個人の賃貸人、多くの利子、配当、資本償還
4. クレジットノート、デビットノート及び返金ノート

そのうえで、素朴な見積もりを崩す二つの除外事項を適用する。2026年1月1日以降、**RM10,000を超える単一取引**は、業種を問わずすべて個別取引でなければならない。そして、e-Invoice Specific GuidelineのTable 3.6にある九つの活動は、まったく統合できない——自動車、航空券、建設契約、代理店及びディーラーへの支払い、賭博の払戻金、電力、電気通信。

月に3台の車を売る整備工場なら、ポータルの作業量は取るに足らない。4,000人のポストペイド加入者を抱える電気通信の再販業者はそうではなく、どれだけ統合してもそれは助けにならない。

**自己請求の量が、たいていの意外な落とし穴になる。** 月に40件の売上インボイスと600件の代理店手数料支払いを持つ会社は、その売上元帳が何と言おうと、大量の電子インボイス事業者である。

## ポータルが本当に立ち行かなくなるところ

- **データ入力のコスト。** すべての個別取引文書には、買い手の氏名・名称、TIN、登録番号、住所、連絡先電話番号及びSST番号を、手入力するかスプレッドシートで読み込ませる必要がある。
- **72時間の時計。** 取消及び拒否のできる期間は検証時から起算される。週次でしか提出しない手作業のプロセスは、これらを利用できない。
- **月末の集中。** 統合電子インボイスは、月末から**7暦日以内**に提出しなければならず、これは他のすべての業務に加えて発生する。
- **照合。** ポータルはXML、JSON、メタデータ、グリッド及びPDFの取得を提供する——しかし検証済み文書を自社の元帳に突き合わせるのは手作業である。

## APIがライセンス費用以上にかかるところ

- **デジタル証明書**を取得し、導入し、更新（ローテーション）しなければならない。
- **提出上限は厳格である。** 1回の提出につき100件かつ5MB、1件の文書につき300KB。バッチ分割、必要であればミニファイ化は自社の問題である。
- **二段階の検証。** *Submitted*は*Valid*ではない。構造、コア項目及びコードは即時にチェックされ、署名、納税者、参照文書及び重複は、バックグラウンドでチェックされる。202スタイルの確認応答を成功として扱う連携は、無効な文書を静かに蓄積していく。
- **トークンの扱い。** ログイントークンは60分間有効であり、リクエストのたびに新規発行するのではなく、再利用することが想定されている。レート制限に達すると、`Retry-After`ヘッダー付きの429が返される。
- **マスターデータ。** 供給者及び買い手のTIN、新しい12桁のBRN、MSICコード及びSST番号は、このいずれかが動く前に正しくなければならない。

## APIへの経路を選ぶ

| 経路 | 適する対象 | 注意点 |
| --- | --- | --- |
| **直接ERP連携** | 維持管理されたマレーシア・ローカライゼーションを備えた成熟ERP、又は社内エンジニアリング能力を持つ事業者 | ガイドラインのバージョンが変わるたびの継続的な保守——v4.7とv4.8はいずれも2026年7月7日に公開された |
| **Peppolサービスプロバイダー** | 取引先との相互運用可能な文書交換も望む事業者 | PeppolはMyInvoisの要件ではない；それが要件であるかのように費用を払わないこと |
| **非Peppol技術プロバイダー／ミドルウェア** | 複数の元システム、POS拠点群、又はローカライゼーションのないERP | データの保管責任、退出条件、及び自社自身の認証情報で提出するかどうか |

LHDNは、いかなるプロバイダーについても是認、認定又は承認を行っていない。ベンダーがLHDN承認のステータスを主張する場合は、それを見せるよう求めること。

## 誰も聞かない、仲介者についての問い

SDKは、仲介者は**自社自身のClient IDとClient Secret**を用いて提出し、**自ら**提出した電子インボイスにしかアクセスできないと述べている——納税者が独自に提出した文書を取得することはできない。

契約書に書き込んでおく価値のある、二つの帰結がある。

- **プロバイダーを切り替えても、提出履歴は引き継がれない。** 並行運用期間と、自社自身のアーカイブを計画しておくこと。
- **責任は移転しない。** 1967年所得税法（Income Tax Act 1967）のSection 82Cは義務を納税者に課しており、s.120(1)(d)は違反を犯罪としている。ベンダーの障害は、あなた自身の不遵守となる。

障害について、LHDNは一つの救済を用意している。e-Invoice GuidelineのSection 2.5.4は、MyInvois System自体がメンテナンス又は技術的な理由で停止しており、納税者が自らのコンプライアンス努力を立証できる場合、内国歳入庁長官が個別に事案を評価し、措置を取らないことがあると述べている。これが対象とするのはLHDN側の停止であって、あなたのベンダーの停止ではない。

## 判断の道筋

1. **免除対象か。** 年間売上高がRM1,000,000未満であれば、ここで終わりである。
2. 上記四つのカテゴリーすべてにわたって、**月次の文書数を数える**。
3. **おおよそ百件未満で、ほとんどが統合か。** ポータルを、Excel一括アップロードとともに使う。毎年見直すこと。
4. **数百から数千件で、単一の元システムか。** 自社のERPベンダーに、そのMyInvoisローカライゼーションが何をカバーするか尋ねる——具体的には自己請求種別11から14、及び輸入に係る附属書の項目である。
5. **数千件、又は複数の元システム、又はPOS拠点群か。** 機能一覧ではなく、データの保管責任と退出条件を基準に選んだミドルウェアである。
6. **何を選ぶにせよ、緩和期間が終わる前にそれをエンドツーエンドで検証すること**——第4段階については2027年12月31日、第1から第3段階についてはすでに過ぎている。

## よくある誤り

- **数える前に買うこと。** 自己請求を含む文書数が、この判断の入力のすべてである。
- **Peppolが必須だと思い込むこと。** それは三つあるAPI経路の一つにすぎない。
- **認定の主張を信じること。** LHDNは承認ベンダー一覧を一切公表していない。
- **検証を同期的だと思い込むこと。** 七つの検証機能のうち四つはバックグラウンドで動く。
- **マスターデータのクリーンアップを飛ばすこと。** 古いSSM登録番号や失効したTINは、連携がどれほど優れていても納税者検証機能で失敗する。
- **クリーンなデータでテストすること。** 海外の供給者、TINを持たない個人、クレジットノート及び月末の量でテストすること——壊れるのはそこだからである。

## 次のステップ

先月分の買掛金と売掛金を取り出し、すべての行を個別取引、統合又は自己請求に分類して、数える。その数がメカニズムを決める。そのうえで項目リストを自社のマスターデータと突き合わせること——クリーンアップは、ほぼ常に連携そのものより長い時間がかかるからである。
